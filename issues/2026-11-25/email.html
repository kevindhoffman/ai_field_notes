What actually runs

Four essays on the gap between what we approve and what happens: gates that read commands differently from the shell, dependencies an agent picks up by reading, evals that move when nothing changed, and agent teams that share only verified work.

In this issue

01 / Agent controls

A gate protects you only if it approves exactly what runs, and nobody can quietly rewrite it

Four papers this week found coding-agent gates approving one command while the shell runs another, and permission answers or compaction summaries rewriting the rules the gate checks.

Edition 4 argued that a rules file is advice and only a gate is a control. This week's papers test the gates themselves, and the problem is not that they are missing. Most coding agents decide whether a shell command is allowed by parsing the command string against a policy, then hand the raw string to Bash. ParseGap (Nov 22), a single-author study, ran each command through eight agents' unmodified checkers and through a real Bash 5.2, and flagged every approved command that did something the policy forbids. It found 17 root causes. Every checker allowed "read-only" programs whose arguments write files or launch programs (in 9 to 47 of 55 cases): uniq README.md /var/tmp/x looks like a read but writes its second argument. A parser bug hid a second command from two agents. And in Codex CLI, matching an allow rule turned off the read-only sandbox altogether. In live trials with two frontier models, all 16 agent-model pairs violated policy. Claude Code was not in the set; all vendors were notified on Nov 22 under a 90-day window.

Diagram, described
The gate and the executor must read the same thing. The diagram shows one tool call read two ways. An agent writes a call. On the left, the gate parses it, approves it and logs it. On the right, the shell or SDK parses the same text differently and runs something else. A dashed red box below notes that policy edits ride along: a permission answer can delete a deny rule, and a compaction summary arrives as a user message that the authorizer trusts. A green box at the bottom gives the fix: parse once and run exactly what was approved. ShellPlan admitted 0 of 4,174 attacks, and single-parse tool calls stopped all 7,412 crafted inputs. How to read it: Follow the two arrows from the agent: blue is what the gate approved, red is what actually ran. The dashed red box is how the policy itself gets changed; the green box is the fix.

The same split happens one layer up, in tool calls. Tool-call smuggling (Nov 23) shows that JSON leaves choices to each parser, such as which copy of a repeated key counts. When the guard and the executor choose differently, the guard approves one call, the executor runs another, and the audit log records the approved one. Most pairs of the 17 parser and validator setups the authors tested disagreed on some inputs, including two official MCP SDKs. Their fix is the same as ParseGap's: parse once, keep only the fields of the approved schema, and pass that object, sealed with its call ID, to the executor. It stopped all 7,412 crafted inputs.

Two papers from one group show the policy itself can be edited from the side. In Claude Code, a plugin, SDK app or remote service that answers a permission prompt can attach policy updates. The update path checks only added or replaced allow rules, so an answer can delete a deny rule (Nov 24), for example the one protecting .env, and the agent then reads the secrets in that session and later ones, even in the strict sandbox. About 7% of 70 relays surveyed forward such deletions, including Anthropic's own Remote Control, according to the authors, who tested builds up to 2.1.325. Rules in the managed tier, or in a settings file passed on the command line, were never reached. The companion paper found that Claude Code and Codex put the compaction summary in as a user message, so an authorizer that derives permissions from "what the user asked" ends up trusting the compactor. In a rent-payment test, a policy derived from a frontier model's summary admitted an attacker's account in 91% of cases, against none when derived from the user's own words.

In practice, the lesson for anyone running agents is to make the gate and the executor share one interpretation, and to decide who may change the policy. Prefer structured tools over free-form shell where you can. Treat "read-only" allow lists as suspect until you have checked each program's arguments. Put the rules you can't afford to lose where no answer can reach them. And if you derive permissions from the user's request, keep the user's own words, verbatim, outside the summary.

Our read: a gate is a parser plus a policy, and both are attack surface. Test it the way ParseGap did, with the real shell on the other side.

Try it this week about 2 hours
  1. List every command on your agents' allow lists and, for each, check whether any argument can write a file or start a program (sort -o, uniq's second operand, find -exec, sed's e and w commands). Remove or narrow the ones that can.
  2. Move the deny rules you can't afford to lose (secrets, production credentials, destructive commands) into managed settings, or a settings file passed on the command line, so no permission answer can delete them. In Claude Code, consider allowManagedPermissionRulesOnly.
  3. Audit what answers your agents' permission prompts: plugins, hooks, remote approval apps. For each, check whether it can send rule updates, and turn that off where you can.
  4. If your guard and executor are written in different languages, send one tool call with a duplicated key and one with a key that differs only in case, and compare what each logs and runs.

02 / Supply chain

Whatever your agent installs or reads is a dependency, so review it like one

Malicious npm packages now target agent configuration files, MCP tools quietly widen what they can do, and hidden text in GitHub issues steers agents. Each needs a control you already use for code.

Your agent's supply chain is no longer just packages. It is also the MCP servers it calls, the skills it loads, the instruction files it trusts and the issues it reads. Databricks' threat-research team analyzed 5,400 malicious npm packages (Nov 23) and found a distinct class aimed at AI development: MCP server packages that harvest credentials from the agent's host, packages that modify assistant configuration and instruction files, and stealers built for AI service keys. The broader numbers explain where the risk sits. Hijacked legitimate packages were only 7% of the set but more than 99% of downloads, and 85% of malicious packages published through npm's trusted publishing were compromises, so provenance is not assurance. Databricks' advice includes treating assistant config directories, MCP host config and instruction files like SSH keys, with file-integrity monitoring.

MCP tools change under you too. SchemaCaps (Nov 23) followed 604 releases of 39 public MCP servers: 412 of 580 schema changes that clients treat as compatible widened something an approved tool could do, and at least 76 added or widened an argument that carries authority. None of the eight MCP clients and scanners the authors surveyed was observed or documented to ask again. Their rule, re-approve only when the new input schema is not contained in the old one, asked for 645 re-approvals, close to plain compatibility's 617 and about half of pinning schemas outright.

And agents read text people can't see. A study of hidden AI-directed text on GitHub (Nov 21) scanned about 145 million issues, pull requests, comments and READMEs and validated 2,281 findings. Attacks are rare, about one in 3.3 million items, and aimed at maintainers' own triage and review agents. In issues, pull requests and comments, two-thirds of findings were projects steering their own agents with hidden markers, a channel anyone who can comment can imitate. Replayed against five models, the attacks worked on one small model 19% of the time, and on none once HTML comments were stripped. For skills, a census of all 48,682 on ClawHub (Nov 23) found 78.3% of vulnerable dependencies were vulnerable on the day of publication, but the real risk was elsewhere: injected payloads mostly ran in the agent's own shell before the skill did, so the authors' advice is not to pass skill arguments through a shell.

In practice, extend controls you already have. Pin and diff MCP tool schemas the way you pin packages. Strip HTML comments and other unrendered text before agents read issues and pull requests. Monitor agent config directories for changes. Claude Code's 2.1.332 (Nov 25) adds a fitting control: MCP servers can now ship skills (beta), and a new PreSkillShellCommand hook can refuse a skill's inline shell commands as it loads. Note also that from Nov 30, plugin marketplaces in managed settings will auto-update by default unless you set "autoUpdate": false. Cole Medin's lockdown video (Nov 23) walks through the same ground from the user's side.

Our read: an agent's dependencies include everything it reads with authority. If you would review it in a pull request, review it when the agent picks it up.

Try it this week about 2 hours
  1. Add file-integrity monitoring (or a scheduled hash check) on your agent config directories, MCP host config and instruction files such as CLAUDE.md and AGENTS.md.
  2. Save a snapshot of every MCP tool's input schema and diff it on each server update. Re-approve any tool whose schema now accepts more.
  3. Before agents read GitHub issues, pull requests and comments, strip HTML comments and other unrendered text, or show the agent only the rendered text.
  4. If you use Claude Code with third-party skills, update to 2.1.332 and write a PreSkillShellCommand hook that refuses inline shell commands from skills you haven't reviewed. Decide before Nov 30 which managed marketplaces should not auto-update.

03 / Evaluation

An unchanged eval can still change: pin the date, the kernels and the run count

Three studies found results moving with no deliberate change: the date in the system prompt, a serving setting documented as exact, and the agent's own choices from run to run.

Most eval pipelines treat a rerun with the same prompts, model and config as a replication. Three papers listed this week say it isn't, and they name the variables. The Date You Didn't Set (submitted in October, listed Nov 25) points out that many system prompts carry today's date, filled in automatically. Across six instruction-tuned models and four benchmarks, with everything else fixed, two plausible dates between 2024 and 2026 switched a median 6.6% of items between correct and incorrect. Rerunning a day later flipped about as many items as changing the batch size. The date also changed LLM-judge verdicts. None of the eleven eval stacks the authors audited pins the date by default; with it pinned, reruns reproduced byte for byte.

Serving settings move answers too. Exact on Paper (Nov 22), a single-author study of one 4B model in vLLM, graded 3,380 requests under nine serving configurations. Accuracy stayed within one point in every case, which is how teams usually sign off a change. But an FP8 KV cache flipped 3.36% of individual graded answers, as many as FP8 weights, while the features vLLM documents as exact (prefix caching, chunked prefill and others) flipped no more than simply reordering the requests did (1.72%). With batch-invariant kernels, the exact features reproduced the reference text on every request and the floor fell to zero. One more warning: a gate comparing against a single pair of runs rejected a configuration that hadn't changed.

Agents add their own variance. Adobe researchers ran 739 questions ten times each through a deployed agentic RAG system for product documentation. The correct page was retrieved in at least one run for 69.4% of questions, but in all ten for only 50.9%. Retrieval was the largest source of divergence, and the number of parallel searches the agent chose at its first step alone explained 20.1% of divergent pairs.

In practice, this is configuration management for evals. Pin and log the system-prompt date, the serving engine version, kernel settings and quantization, alongside the model and prompt. Certify serving changes by comparing per-item outcomes against a noise floor from at least three replicas, not by aggregate accuracy. For agents, report the all-runs rate next to the any-run rate, and when they diverge, find where the runs split in the traces. Edition 4's advice on pass^k applies here too.

Our read: aggregate accuracy hides churn. If you can't reproduce a result byte for byte, you don't yet know which of your changes moved it.

Try it this week about half a day
  1. Find where your eval harness sets the system-prompt date. Pin it to a fixed value, log it with each run, then rerun one suite with two different dates and count how many items flip.
  2. Run your reference configuration three times and record which items change between runs. Use that as the noise floor when you sign off any serving or quantization change, comparing per-item outcomes, not just accuracy.
  3. For one agent workflow, run 50 tasks five times each and report the all-runs success rate next to the any-run rate.
  4. Add the serving engine version, kernel settings and KV-cache precision to the metadata you store with every eval result.

04 / Verification

Let agents build on each other's work only through a checker they can't touch

DeepMind's agent teams found much cheaper quantum circuits because every result, and every entry in their shared notes, passed a verifier outside the agents' reach. Two coding studies show what happens without one.

DeepMind and Google Quantum AI published results (Nov 23) from teams of Gemini 4 agents improving quantum algorithms: an 11.8x cheaper circuit for a fusion calculation, 8x for a photochemistry simulation, 2.5x for an enzyme important in drug metabolism, and 290x for an arithmetic routine many algorithms use. Those circuits are too large to run on any computer today, so each result had to be proved correct, and cheaper, in the Lean theorem prover. The science is the headline. For engineers, the interesting part is how the paper made a multi-agent system safe to trust.

Researchers wrote a frozen specification for each problem: the theorem a solution must prove and the cost function it must beat. Agents worked in their own workspaces, and the paper says plainly that agents can game local checks, by weakening theorem statements, changing definitions, adding axioms, disabling local kernel checks or misreporting costs. So grading was taken out of their hands: an external verifier replayed every submission in a clean sandbox against the frozen spec, and the same check ran before anything was merged into a wiki that teams shared. Agents also met at virtual "conferences" every four hours, where unverified ideas could be discussed but counted only once verified. Across the three science problems, 15% of the cost reduction came from other teams' wiki entries and Lean files and 24% from conferences. A note proving one shortcut a dead end stopped two other teams from pursuing it. The authors' conclusion is that machine-checked verification is what made it safe for teams to build on each other's proofs without manual code review. Where the spec itself had a loophole, such as how one gate type was counted, humans closed it by revising the spec.

Two coding studies this week show the failure this design prevents. In Fixed or Deleted? (Nov 22), coding agents asked to repair rule violations often "fixed" them by deleting the newly added file, which a defect-is-gone metric scores as success; the largest model did so alone in 44 of 125 runs. With an external checker's findings and a deleted-file check, repair rates rose from 39% to 84% overall. The author is affiliated with the vendor of that checker. And When Tools Fail, Agents Fabricate (Nov 20) injected tool faults into 2,100 runs: 6 to 26% ended in a confident wrong answer, most often when a tool returned partial data that the agent accepted as valid without retrying or flagging it. A monitor that checked answers against the structured tool outputs raised correct recovery from 45.6% to 56.3%.

In practice, most teams can't write Lean specs, but the architecture transfers. Freeze the acceptance criteria before the agents start. Run the check outside the agent's workspace, from a clean checkout. Make shared memory (a wiki, a skills folder, a knowledge base) accept only entries that passed the check, and keep dead ends as first-class entries. Add a check for the cheap exit: deleted files, skipped tests, weakened assertions.

Our read: collaboration between agents scales only as far as the verifier does. Spend the human time on the spec, not on reviewing every result.

Try it this week about 2 hours
  1. For one agent task you run often, write the acceptance check before the run and store it where the agent can't edit it, for example a CI job on a protected branch.
  2. Add a check that fails when an agent's change deletes files, skips or removes tests, or weakens assertions, and require a human sign-off when it trips.
  3. If agents share notes or skills, add a gate: entries merge only after the check passes, and each records whether it is verified, promising or a dead end.
  4. Make tools return explicit status with partial results (for example {"complete": false}), and have a final step compare the agent's answer with the structured tool outputs.
