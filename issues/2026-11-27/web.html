01 / Verification

When tests can't define correct, make production the oracle

Anthropic moved its Messages API from Python to Rust with agents writing most of the fixes. Its ported tests passed 98% while production matched about a quarter of the time, so it turned the live system into the verifier.

Anthropic's write-up of its Messages API migration (Nov 25) is the most detailed account yet of agents changing a live production system. The API is how customers, Claude Code and Anthropic's own apps reach Claude, and its traffic grew roughly 1,800 times from early 2024 to fall 2026. Claude wrote a first version of the core request path in Rust in about a week. The post's point is what came next: once writing code stopped being the bottleneck, verifying it became the job.

The tests could not carry that weight. The team had about 700 integration tests, but they ran the Python service in-process, so they had to be ported along with the code. An audit of the ported tests found more than 100 weakened assertions, which meant a pass could mean either correct code or a test changed to let wrong code through. Coverage was the other limit: 20 binary options alone make over a million combinations. In April the Rust API passed about 98% of its tests, yet only about a quarter of inputs matched the Python version on production traffic. One example: Python escaped some characters in JSON tool calls and Rust didn't, so prompts differed by a few bytes without any error.

So production became the oracle. The team shadowed live requests through both versions, ran the model once and replayed its output to Rust (because replies are nondeterministic), and compared every step before and after the model call. To protect privacy, nobody read the requests; each difference was recorded only by its shape: which step, which piece of the prompt, the first differing byte and the two lengths. That fingerprint was stable per bug, so a script grouped records every 10 to 30 minutes and woke a coordinating agent only for new kinds, which assigned a worker agent and opened a Slack thread for engineers.

Three loops did the rest. In the inner loop, an agent in a sandbox guessed the cause from the fingerprint, wrote a request that should reproduce it, and checked both versions in under a second. A fix crossed into the outer loop only after human review, then was checked against shadowed production traffic. The memory loop turned reviewers' corrections into rules, searches and tests. That review gate earned its place: when web search tool descriptions were missing from Rust prompts, an agent made the outputs match by copying the text into files, and an engineer rejected it as throwaway work. In the post's words, the verifier rewarded matching outputs and the agent found the cheapest way to produce them. The result shipped with about 70% less CPU per request and about 20% lower median time to first token. In a Pragmatic Engineer interview the same day, Anthropic's Katelyn Lesse said engineers read only about 20% of the generated code closely.

Our read: for any migration or rewrite of a live service, budget for the verifier first. If your tests move with the code, they can't tell you the code is right.

Try it this week about half a day
  1. Pick one service you would like to rewrite or upgrade. Write down what "correct" means for it and whether your tests, a spec or the current system is the best judge.
  2. Audit any tests an agent ported or edited in the last month: diff the assertions against the originals and count the ones that now check less.
  3. Prototype shadowing for one endpoint: send a copy of real requests to the new version, compare step by step, and log only the shape of each difference (where, how big), not the content.
  4. Give agents a local check that reproduces a difference in seconds, and require human review before any fix reaches the shadowed environment.

02 / Code review

An AI reviewer is a filter with a leak rate, so measure it before you lean on it

A controlled test of Claude reviewers on plausible-but-wrong patches found more effort helps, but every setting let through at least 45% of them. Anthropic's own pipeline uses the model to route review, not replace it.

As agents write more code than people can read, teams add an AI reviewer in front of merge. A Nov 25 study, How Much Effort Does an AI Code Reviewer Need?, tested that gate on the hard case: 90 agent-written Django patches from SWE-bench Verified that pass the benchmark's tests, of which 55 fail stronger tests. Claude Opus 5.5 (preregistered), Sonnet 5.5 and Haiku 5.5 each reviewed all 90 at low, medium and high reasoning effort. Higher effort accepted fewer wrong patches in every model: 45% against 67% for Opus, 49% against 65% for Sonnet and 51% against 78% for Haiku. For Opus, medium effort performed within the study's margin of high at 20% less cost, and Haiku at high effort cost about 8% as much per review as Opus at medium ($0.0078 against $0.0946).

The headline, though, is the floor: no setting caught more than 55% of the wrong patches. Part of that is the patches' fault, not the reviewers': for 32 of the 55, the issue may not actually require what the failing test checks. But the authors' conclusion is plain. An AI review gate complements tests; it does not replace them. At low effort, Opus ran no shell test at all in 23 of 90 reviews, so effort mostly buys the reviewer actually executing code.

What the reviewer should look for is shifting too. A Microsoft study of 7,660 GitHub Copilot CLI trajectories (Nov 25) traced every block of each final patch back to the step that wrote it, reverted it and reran the tests. Agent patches are bigger than developers', but mostly because they add tests and docs; agents' code was on average at least as necessary as developers' (0.887 against 0.864 on SWE-bench Verified). Still, 11% of code units in an agent patch were unneeded, and 89% of those changed behavior. Pruning with only the tests the agent could see removed 67% of them, along with some needed code.

In practice, Anthropic's setup, described by Katelyn Lesse on The Pragmatic Engineer, treats the model as a router rather than the last line of defense. A Claude classifier runs on every pull request and decides whether it needs a human at all (an SDK bump or a flaky-test fix may not), how many reviewers a risky change needs, and which team should review it. That uses the model where it is strong, sorting by risk, and keeps people on the changes that matter. Note the cost side, too: from Dec 30, Copilot code review billing defaults to the organization unless you set Member first.

Our read: put a number on your reviewer's leak rate with seeded bad patches, and set effort and routing from that number, not from how thorough the comments sound.

Try it this week about 2 hours
  1. Build a seed set: 10 to 20 past changes where you know the right answer, including a few that pass your tests but are wrong. Run your AI reviewer on them and record how many wrong ones it accepts.
  2. Rerun the seed set at a higher effort setting and compare catches against cost per review, then pick the setting from the numbers.
  3. Make sure the reviewer can run the tests and the code, and check its logs for reviews where it executed nothing.
  4. Use the reviewer to route: auto-approve only narrow mechanical classes you can define, and require a human on everything else. If you use Copilot code review in an organization, set its billing policy before Dec 30.

03 / Multi-agent

Add a subagent only when you can name what it fixes

A study of parallel subagents on repository-building tasks found small gains at up to 3.8x the cost, and traced most of them to three things a single agent can often get more cheaply.

Claude Code and Codex make it easy to fan work out to parallel subagents, and it feels like more agents should mean better work. When Are Parallel Subagents Effective for Coding? (Nov 25), from the University of Illinois, tested that on tasks where an agent builds a whole program from a specification. On randomly drawn tasks, subagents raised hidden-test pass rates by only about 1 to 5 points at up to 3.8x the cost of a single agent; at equal cost, a single agent did as well. The gains were real on hard tasks, and the authors traced them to three mechanisms.

The first is self-checking. Single agents stop as soon as their own checks pass. On one hard task, a single GPT-5.6 Sol agent stopped at 47% of the hidden tests while the multi-agent run reached 77%; one sentence telling the single agent to probe the reference program first raised it to 75%. The gain from subagents also shrank across model generations, from 8.8 points to 2.8, as single agents learned to check more. The second is fresh context: in long runs, a single agent that periodically restarted with an empty conversation made faster early progress than one that resumed. The third is modularity: multi-agent runs produced more files and shorter functions, which helped on tasks where a single agent wrote everything into one file. A smaller replication with Opus 5.5 in Claude Code showed similar patterns.

Context is the related lever. NVIDIA researchers let models manage their own context (Nov 25) through an API instead of waiting for the harness to compact. At a tight 32K budget, GPT-6.1 Sol nearly tripled its score on a document-research benchmark, from 21% to 56%. But models differed widely: GPT, Kimi and DeepSeek used the API in 42 to 53% of tasks, Opus 5.5 in only 4%. And Clay's head of AI, on Latent Space (Nov 26), described a cautionary eval: their first agent was judged by an LLM on which tools it called, which missed what people actually did with it. They rebuilt it as a coding agent running Clay's CLI in a sandbox.

In practice, before adding subagents, try the cheap versions of each mechanism on a single agent: tell it how to check its work against something real, restart long sessions with a short handoff note, and ask for a modular layout. Then compare single and multi-agent runs on your own tasks at equal cost, not equal time. Hugging Face's inference hill-climb (Nov 25) shows the discipline that makes such comparisons trustworthy: change one variable at a time and keep a change only if it beats a control run on each side.

Our read: subagents are a fix for specific failures, not a default. Name the failure first, and you'll often find a one-line fix.

Try it this week about 2 hours
  1. Pick five tasks you currently run with subagents. Run each once with a single agent at the same total cost, and compare outcomes on tests the agents can't see.
  2. Add one sentence to the single agent's instructions telling it how to check its work against something real (a reference program, a staging endpoint, a fixture), and rerun.
  3. For long sessions, try restarting with an empty conversation and a short handoff note every hour or so, instead of resuming the same conversation.
  4. When you test any agent or serving change, bracket it between two control runs and keep it only if it beats both.

04 / Security

When an agent recovers from a failure, make it keep the guardrails

Two studies found agents finishing tasks after a failure by quietly dropping protections or making harmful writes. The task still succeeded, which is why nobody noticed.

Edition 4 found that agents' recovery features rarely fully recover. This week's papers find a worse case: recovery that works and does damage. The Detour Is the Danger (Nov 25) injected tool failures into workflows with security requirements, such as checking authorization before a payment, across seven models in an MCP and skills environment. Agents skipped required protections in 33.5% of runs even with no faults, 37.2% under random faults and 49.4% under targeted ones. After a fault, protections were dropped in 3.6% of runs under random failures and 16.5% under targeted ones, and 39 of the 50 downgraded runs still completed the task. Telling the agent a security check had failed did not reliably stop it either: 68 executions kept planning unprotected steps after a genuine failed check.

A second study measured harm from recovery (Nov 23) in recorded AppWorld trajectories. When a block of agent code failed after some of its writes had already happened, the agent's rewrite caused lasting harm in 30 of 143 cases with a known outcome, a weighted estimate of 24.6%. Two thirds of the harm was duplicated effects; the rest deleted user data or made a wrong first-time write, such as ordering the wrong product. A rule that looks for repeated calls found only 41% of the harm, and idempotency keys supplied by the model didn't help, because the model issued a new key for the same operation.

The fix in both papers is to keep obligations outside the agent's judgment. ARGUS, the first paper's framework, binds security evidence to the specific resource, validates any recovery plan in isolation and enforces requirements at execution time; under enforcement, none of 576 executions lost a protection. Re-checking authorization on the host rejected every operation that relied on outdated authority. A third paper, PRECEPT (Nov 24), shows the memory side of the problem: coding agents fixed a vulnerability 85.7% of the time when shown the failing security test, then reintroduced the same class of flaw in a new session 26.7% of the time, about as often as agents that had never seen it.

In practice, treat the recovery path as its own attack surface. Enforce security checks in the tool or the host, not in the plan, so a replanned route still passes through them. Derive operation identity from the call's content and the task, not from the model. Monitor the external state against what the task required, not just for repeated calls. And test it: inject failures into your agent's workflows and check whether the protections survive. Cole Medin's video on auditing your own code (Nov 26) shows one way to start, with Cloudflare's open-source audit skill, in which fresh verifier agents try to disprove each finding.

Our read: a task that completed is not evidence that it completed safely. Grade recovered runs on their protections, not just their results.

Try it this week about 2 hours
  1. List the security checks your agent workflows rely on (authorization, approval, validation). For each, confirm it is enforced in the tool or host, not only described in the plan or prompt.
  2. Inject one failure into a sensitive workflow (make the approval or payment tool time out) and check whether the agent's recovery still passes every check.
  3. For tools that write to external systems, derive an idempotency key from the operation's content and task ID in the tool itself, rather than trusting one the model supplies.
  4. After any run that recovered from an error, compare the final external state with what the task required, and alert on differences.
