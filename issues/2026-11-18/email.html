AI Field Notes

The harness does the work

Five essays on what surrounds the model: scripts instead of single tool calls, checks the harness runs instead of rules the agent reads, sandboxes that hold the code and not the secrets, context designed for the cache, and evaluations built from your own work.

In this issue

What surrounds the model decides what you get

The fresh lead is Claude Code's Code Mode, which lets the agent write a script instead of making one call at a time. The rest of the week's evidence points the same way: rules enforced in the harness beat rules in the prompt, execution belongs in a separate box, the prompt cache rewards context that only grows at the end, and two models that tie on a leaderboard can be far apart on real work.

01 / Agent tooling

Experimental feature

When a task takes ten tool calls, let the agent write one script

Claude Code's new Code Mode turns a chain of tool calls into a small program. It saves tokens and turns, and it moves your safety checks somewhere new.

Most coding agents work in a strict loop: ask for one tool call, read the whole result, decide on the next call. Claude Code's Code Mode, documented on Nov 16 and still experimental, breaks that loop. Claude writes a short piece of JavaScript that makes the calls itself, and Claude Code runs it in your session. One script can run commands in parallel, feed one result into the next call and hand back only the part Claude needs to read. Version 2.1.326 of Claude Code (Nov 16) extended it to agent teams. Ray Amjad's Nov 16 video calls it the biggest change to Claude Code's harness yet; that is his opinion, but the idea has evidence behind it.

Diagram, described
Code Mode moves the loop from the model into a script. The diagram compares two ways an agent uses tools. In the top row, without Code Mode, the model and the tools alternate: model, tool, model, tool, model, and every full result lands in the context window. In the bottom row, with Code Mode, the model writes one script; the harness runs the tool calls (a search, an edit, the tests) in parallel and returns only the part the model needs. A note underneath says that rules and hooks still see each tool call, but auto mode's classifier sees only the code. How to read it: Compare the two rows: the top row pays a model turn for every tool call; the bottom row pays once and keeps the raw output out of the context window.

The docs' own example shows the shape. Asked to raise a retry limit, Claude writes four lines: search for the file with rg, take the first hit, edit the value, then return the file path and the test output. In a normal session that is at least three round trips, each dropping a full result into the context window. A preregistered study posted on Nov 14, Beyond Plain MCP, tested the same idea on MCP tool catalogs of up to 1,958 distractor tools with three open-weight agents. Letting agents write scripts against tool stubs cut token use by 70 to 90 percent and raised success. The surprise was what mattered most: declaring the shape of each tool's return value in the stub swung success by up to 39.5 points for weaker agents, more than putting a tool-picking router in front, which made no significant difference.

In practice, the docs point Code Mode at three kinds of work: a change repeated across many files, a search whose results need filtering before anyone reads them, and independent commands that can run at once. The docs' starter prompt is a good first test: ask Claude to read every Markdown file in a project and list links to local files that don't exist. Then press Ctrl+O to read the code it wrote. If you build your own tools or MCP servers, the paper's lesson transfers directly: a model writing code against your tool needs to know what comes back, so describe the returned fields, not just the inputs.

The tradeoffs sit in the permission layer. Each tool call inside a script still passes your deny and ask rules and your PreToolUse hooks under its usual name. But in auto mode, the classifier reviews the script before it runs, not each call, and it cannot see values computed at run time, such as a path pulled from search output. Hooks that match shell commands need to handle compound commands, because a git push can arrive as cd 'app' && git push. Code Mode only runs in an interactive terminal session: not with -p, the Agent SDK, VS Code, the Desktop app, cloud sessions, Bedrock or a gateway. A project's settings file cannot switch it on, and administrators can block it with a managed setting of 0.

Our read: the unit of agent work is moving from a single tool call to a small program. Review, permissions and logging were built around the call, and they need to follow the program.

Try it this week about 45 minutes
  1. Check claude --version is 2.1.323 or later, start a session with CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1 claude in a repository you know, and give it the docs' prompt: list the links in every Markdown file that point to local files that don't exist. Press Ctrl+O to read the script.
  2. Run the same task in a normal session and compare the number of tool calls, the time and the tokens used.
  3. If you rely on PreToolUse hooks to block shell commands, test that a blocked command is still caught inside a compound command such as cd app && git push. Add a hook that matches REPL and logs tool_input.code, so every script is on record.
  4. If you maintain tools or an MCP server, add the return shape (field names and types) to each tool's description.

02 / Reliability

Check the tool's answer in the harness, before the model can believe it

Four studies this week measure what happens when a rule lives in code that runs next to the agent instead of in text the agent reads. The difference is large and consistent.

Edition 1 argued that limits written into prompts get reasoned around. This week brought measurements, and they extend the point from security to everyday correctness. The sharpest is SilentGuard (Nov 16). Its starting observation is uncomfortable: APIs fail silently. A request with a misnamed filter can be partly ignored and still return HTTP 200 with a plausible, wrong answer. The authors found such failures in 11 of 15 public research APIs, with counts inflated by up to 691 times. Checklists, reviewer models and LLM judges all ask the model to notice, and models often notice and answer anyway. SilentGuard instead tests each result in the harness against invariants any correct API must satisfy, and withholds values that break one. Across seven open models, wrong answers on the targeted faults fell from 74.0% to 1.7%, and on three frontier models from 70.2% to 0.5%. Showing the same check as a warning left 70.1% wrong. The harness doesn't fix the data; it makes the agent abstain.

Rules about actions behave the same way. Runtime Contracts for Coding Agents (Nov 14) compared engineering rules enforced as executable checks while the agent works against the same rules in the prompt, retrieved as guidance, or checked afterwards. With enforcement, an independent oracle found no violations in 104 paired runs, against 21 to 55% of runs with no rules. The details are the useful part: prompted rules did not stop recursive deletes of scratch directories, and checks after the fact could repair file edits but not commands that had already run. The study used low-cost models and one small fixture.

Even budgets follow the pattern. A placebo-controlled study of 5,835 runs, Does Your Agent Need to Know Its Budget?, found that enforcing a token cap cut tokens per solved task about twelvefold (at a cost of 20 points of solve rate under a calibrated cap), while telling the agent about the budget never helped. An unrelated sentence added to the prompt raised resolution by 7.2 points, a reminder that prompt-wording experiments without a placebo arm can mislead. And Reversibility Classes (Nov 17) gives approval gates a better key than read versus write: whether an action can be undone. Its session guard caught all 29 attributable attack runs, against 18 for a read/write proxy, while adding nine approval prompts across 1,209 benign runs. The authors note their tool ratings were not independently reviewed.

In practice, this adds up to three checkpoints in your harness. Check results before the model sees them: a filtered count can't exceed the unfiltered one, returned IDs should match the ones requested, dates should fall in the range you asked for. Check actions before they run, because nothing undoes a command after it has executed. And gate approvals on reversibility, so people are asked about the deletes and the sends, not every file write. Claude Code's PostToolUse and PreToolUse hooks are the natural places for the first two in that tool; most agent frameworks have equivalents.

Our read: a rule the agent reads is a suggestion. A rule the harness runs is a guarantee about what reaches the agent and what leaves it.

Try it this week about 2 hours
  1. Pick one API your agent relies on and write two or three invariants for it (filtered count ≤ total, IDs returned match IDs requested, dates within the requested range). Run them in a post-tool hook and replace failing results with an explicit error.
  2. Take the most dangerous rule in your CLAUDE.md or AGENTS.md, such as “never delete outside the workspace”, and turn it into a pre-tool check that blocks the call.
  3. Tag your agent's tools as read-only, undoable, undoable only with a snapshot, or irreversible, and require approval only for the last two.
  4. Next time you A/B a prompt change, add a third arm with an unrelated sentence of the same length.

03 / Security

Run the agent's code in a box, and keep the agent and its secrets outside it

A new sandbox pattern from Simon Willison, plus two papers on how agents get attacked through legitimate tools, point to the same design: contain the execution and control the credentials.

Most agent sandboxes put the whole agent in a container. Simon Willison and the research lab Prime Radiant released another option on Nov 17: the external sandbox. The agent runs outside, on your machine as usual, and whenever it wants to execute code it sends that code to a sandbox server over a localhost API. They published three servers with the same API: one runs Alpine Linux inside WebAssembly with v86, one uses Apple Containers, and one uses Microsoft's Quicksand library, which bundles QEMU and Alpine into a Python package. Pi, Claude Code or Codex can be configured to use them. Each sandbox can sit behind an HTTP allow-list proxy that controls which hosts the code may reach, and that can swap in credentials so authenticated API calls work without the secret ever passing through the agent. Willison's motivation is trying local models without worrying that a mistake or a prompt injection damages the machine.

Diagram, described
Keep execution, egress and secrets in three separate places. The diagram shows the external sandbox pattern. A coding agent (Claude Code, Codex or Pi), which holds no secrets, sends code over a localhost API to a sandbox server that runs it, using v86, Apple Containers or QEMU. The sandbox's network traffic passes through an allow-list proxy that permits only approved hosts and injects credentials, and only then reaches the internet and APIs. A red box on the left notes what scanners miss: harmless tools chained across turns reached 73 to 85 percent attack success, and scanners caught none of them, per the Compositional Exploits paper. How to read it: Follow the right-hand column from agent to internet: each box is a place where you control something. The red box is why per-tool scanning isn't enough.

Why put the boundary at execution rather than at the tools? A Nov 15 paper, Compositional Exploits in Autonomous Coding Agents, shows that checking tools one at a time misses the attack. The agent chains individually harmless tools across turns, passing data through workspace files, environment variables and chat memory. On a 360-task exploit suite, unprotected Gemini Flash models completed such chains 72.9 to 84.5% of the time, and five leading tool scanners detected none of the tools involved. The authors' own defense, which works at the operating-system level (Landlock file rules, seccomp socket filters and a short-lived proxy), blocked every attack while keeping a 98.0% solve rate on benign work. It is their benchmark and their defense, so treat the 100% as a design argument.

The tool layer has its own identity problem. When Tool Names Are Not Identities (Nov 16) shows that an attacker who only runs another MCP server can get requests meant for a legitimate provider routed to their tool. The worst cases combine an identical tool name, a description aligned with the task and a compatible schema, but descriptions that claim authority could do it even without a name clash. On the supply side, GitHub added a strictPluginOnlyCustomization setting on Nov 16 that lets enterprise admins require skills, custom agents, hooks, MCP servers and executable extensions to come only from plugins or managed settings.

In practice, a containment design has four parts. Code runs somewhere other than where the agent and your files live. Outbound traffic goes through an allow-list. Secrets are added at the proxy, so a compromised session has nothing to steal. And tools come from a source you control, with names that can't be spoofed by whatever other server is connected. None of this depends on the model behaving well, which is the point.

Our read: scanners audit parts, but attacks are assembled from parts. Contain the assembly.

Try it this week about 2 hours
  1. Try one of the three external-sandbox servers from Willison's post with a throwaway repository, and turn on the allow-list proxy with only your package registry allowed. Note what breaks.
  2. Search your agent's environment and config for API keys. Move one of them behind a proxy that adds it to outgoing requests, so the agent never sees it.
  3. List every MCP server your agent connects to and look for duplicate or near-duplicate tool names. Remove or rename them, and pin the servers you use.
  4. If you administer Copilot Business or Enterprise, try strictPluginOnlyCustomization for MCP servers and extensions first.

04 / Cost

Your prompt's opening is a cache key: design context so it only grows at the end

With cached input now a twentieth of the price on some frontier models, the cheapest context strategy is often the one that never edits the past.

Long agent sessions resend their whole history on every turn, and providers charge much less for the part they have already seen, the cached prefix. That discount just got bigger. OpenAI's GPT-6.2 Astra, released Nov 17, costs $8 per million input tokens and $40 per million output, but cached input drops to $0.40 per million, down from $1 for the previous Astra, as Simon Willison noted. That makes cached tokens a twentieth of the price of fresh ones, and it changes which context tricks actually save money.

Diagram, described
Edits early in the history turn cheap cached tokens back into full-price ones. The diagram shows two rows of a prompt. In the first, the new turn is appended at the end, so the system prompt and turns one to four stay cached and cheap. In the second, an old tool output is pruned from the middle; the system prompt stays cached, but everything after the cut is billed at full price. A box underneath gives the Context Has a Price results with cached input at a tenth of the price: adding retrieved code raised cost 33 to 42 percent, and pruning raised it 38 to 116 percent, although the same pruning saved 19 to 36 percent when there was no cache discount. How to read it: Green is billed at the cached rate, red at the full rate. The top row is the shape to aim for.
See the diagram in the full article on the web →

A Nov 17 paper, Context Has a Price, measured this across more than 20,000 runs of open models on SWE-bench tasks, counting uncached input, cached input and output separately. Two popular ideas backfired once the cache was priced at a tenth of fresh input. Adding retrieved code up front cut the agent's read and search commands by 18 to 34% but raised cost by 33 to 42%, with no measurable gain in tasks solved. Pruning old tool outputs saved 19 to 36% when there was no cache discount, and cost 38 to 116% more when there was one. The mechanism is simple: the cache covers an unchanged prefix, so any edit early in the history makes everything after it fresh again. The authors add two warnings: shorter prompts can make agents take more steps, and experiments running at the same time can share cached prefixes and distort cost comparisons.

What does save money is removing work rather than rewriting history. Microsoft Research's TokenEconomizer (Nov 16), an open-source plugin from UC Berkeley and Microsoft, profiled Claude Code on SWE-bench and found that once a repository had five completed tasks, 30% of tool calls repeated an action from an earlier task, and the 17% of tasks that failed accounted for 32% of spending. It learns one-line repository notes from past sessions, trims tools the agent never uses and nudges agents out of failure loops. Across 277 tasks and five agent-model combinations it cut mean cost per task by 18.4 to 30.9%, counting its own model calls. Routing now respects the cache too: Hugging Face's Inference Providers moved to OpenRouter's router on Nov 16, which keeps a conversation on the provider holding its prompt cache and accepts a stable session ID header to make that explicit.

In practice, design context to grow only at the end. Keep the system prompt and tool definitions stable and first; move timestamps and anything that changes into the latest message; and when you must compact, do it rarely and in large steps rather than trimming a little every turn. Log cached and uncached input tokens separately for every run, and judge any context change on cost per solved task, including how many steps the agent took. If you serve open models to several customers yourself, note a further paper this week, Where the Savings Go: a single timing probe could tell whether another tenant had sent a given text of 256 tokens or more, by watching how a shared prefix cache sped up the queue, and hiding the hit alone failed on both vLLM and SGLang.

Our read: under prefix caching, the history is an append-only log with a price on every edit.

Try it this week about 90 minutes
  1. Pull a day of your agent's usage logs and compute the share of input tokens billed as cached. If it is low, find what changes near the start of the prompt: timestamps, reordered tools, per-turn summaries.
  2. Move anything dynamic out of the system prompt and into the latest message, then measure the cached share again.
  3. Before shipping a retrieval or context-pruning change, run it against the old setup on 20 tasks one at a time (not in parallel) and compare uncached, cached and output tokens, steps and tasks solved.
  4. On a repository your agents work in daily, look for the tool calls they repeat every session and write the answers into the project's agent notes.

05 / Evaluation

Vendor claim

Choose models with your own work, then check whether more work got done

Two models that tie on a leaderboard were 17 points apart on one team's real tasks, and a natural experiment found that a higher-scoring coding model didn't raise merge rates at all.

Epoch AI tested six models on tasks taken from its own work (Nov 17) and graded every output by hand against the standard it expects of its staff. No model met that standard on any task. Claude Fable 5.2 and GPT-6.2 Astra roughly tie on Epoch's own capabilities index, yet Astra averaged 65%, 17 points below Fable 5.2. The gap came from judgment, not knowledge: on a data-center research task Astra left out estimates it had the evidence for because it wanted a separate source for every number. On that same task Fable 5.2 scored 97.5% and Opus 5.5 87.5%, which Epoch counts as contractor level; Opus 5.5 finished in just under three hours, against about 16 for a contractor. Every model reused existing ideas when designing experiments, and when asked to compare their own reports with a human's, the models preferred their own in every case but one. Epoch notes the limits: one run per task, subjective grading.

A second study asks whether leaderboard gains show up in daily output. Higher-Scoring Coding Models Did Not Get More Work Done (Nov 17) uses what the author describes as a 19-day suspension of Claude Fable 5 access in June, during which most users fell back to Opus 4.8, 11 points lower on SWE-Bench Pro. Comparing 297 affected developers with 8,908 who stayed on Opus 4.8, access to Fable 5 raised the 7-day pull-request merge rate by just 1.4 points, not statistically significant, and five other model upgrades showed no gain either. Merge rate is a coarse measure and this is one author's analysis, but it is the right kind of measurement.

The tooling for doing this yourself arrived the same week. GitHub's Copilot Evals (public preview, Nov 17) builds repeatable tests for your skills, custom agents and MCP tools with an /eval command, and compares runs before and after a change. GitHub's benchmark site added a harness view that runs the same model in Copilot CLI, Claude Code and Codex CLI and plots solve rate against cost per task; GitHub built that comparison, so read it as a vendor's. Databricks' new AI Index (Nov 16) reports that, replaying traces from its own workloads, it judged an upgrade from Opus 4.8 to Opus 5 not worth the cost and stayed put. As Satya Nadella put it on The Pragmatic Engineer, “your private evals will matter more.”

In practice, use two measurements. Before choosing, run a small private task set drawn from your real work, with a known good output and a rubric, and grade it blind yourself; Epoch scores each criterion from 1 to 4. After switching, watch an outcome you already track, such as pull requests merged within a week, reverts or tickets closed, for two weeks before and after. Don't ask a model to judge its own output against a human's: Epoch's results show it will pick its own.

Our read: a benchmark tells you what a model can do; only your tasks and your outcomes tell you what it will do for you.

Try it this week about half a day
  1. Pick five tasks your team finished last month where you know what good looks like. Write a 1–4 rubric for each, run two candidate models, and grade the outputs blind.
  2. Before your next model switch, record a baseline for two weeks: pull requests merged within seven days, reverts, or another outcome you already measure. Compare the two weeks after.
  3. If you use Copilot, run /eval on one skill or custom agent, change it, and rerun to see whether the change helped.
  4. If you use an LLM judge, test it once: give it your output and a human's without labels and see which it prefers.

  • Skills go stale when the environment changes
    A Nov 17 paper, When Agent Skills Go Stale, found that skills that helped before an environment changed could cut task success by more than 10 points or raise cost by nearly 40% afterwards. Its fix replays checks from past successful runs to find and repair outdated parts, improving accuracy by up to 67 points over reusing the stale skill. A useful follow-up to Edition 1's skills essay: test skills whenever the tools they describe change.

Research corner

Interesting science with no immediate application yet. Good to know, not urgent.

  • Can models tell when they're being tested for alignment?
    METR had investigator agents explore 19 alignment evaluations and 36 capability tasks and estimate which were which. Discrimination has improved over the past year, and Opus 5.5's averaged scores ranked every alignment eval above every capability task. If models can spot tests, they may behave better in them than in deployment; METR publishes its prompts and rubric.
    METR · Nov 16, 2026 · free
  • Agents that spend money to improve models
    Jack Clark's Import AI 481 describes FrontierML, a benchmark where agents get $10 to $200 and 12 hours to improve a model on 21 machine-learning tasks. By his account, human researchers still gained more per budget than the best model, Opus 5.5. We could not reach the benchmark's own site, so these figures are as reported.
    Jack Clark, Import AI · Nov 16, 2026 · free
  • Training without a learning-rate decay
    Sebastian Raschka's quick note sorts recent open models by learning-rate schedule (cosine decay, warmup-stable-decay, or a constant rate with checkpoint averaging) and suggests the last could become a trend, because it doesn't require fixing the training length in advance.
