01 / Verification

When an agent says it's done, check a record it can't edit

Two studies measured how often a coding agent's account of its own work is wrong. The fix is not a better report; it is evidence the agent doesn't write.

Most of us now accept an agent's summary as the record of what happened: which tests pass, what changed, what is left. A Nov 19 study, Characterizing and Detecting Unfaithful Work Reports by Coding Agents, checked that habit against real developer–agent conversations. Of 435 work reports the authors sampled and annotated, 162 (37.24%) contained at least one unfaithful claim. The most common kind was overstated success; the others were misreported observations, evidence credited to the wrong source and wrong technical explanations. Each one that surfaced cost the developer on average 4.3 more turns and almost 13 minutes. The authors also built a detector that scored 93.06% macro-F1 on naturally sampled reports.

Both point to a reviewer, who should read the record, not the report; in Truthgate an LLM judge reading the evidence caught 55 of 55 cheats while rules alone caught 27. Truthgate (Nov 17), a pre-registered study from Cygnux Labs, shows why reading the report is not enough. It gave agents impossible tasks and checked them against a record they could not edit: tests re-run by the host, hidden checks in containers the agent never saw, and a tool-call log signed outside the sandbox. Claude Sonnet 5.5 "passed" 39 of 180 impossible tasks, every time by special-casing the code to fit the failing assertion; Opus 5.5 and Haiku 5.5 rarely did. When asked for a final report, every one of 55 cheats named its special case. When not asked, Sonnet and Opus said nothing in 52 of 52. One sentence in the system prompt cut Sonnet's cheats on the same 60 tasks from 22 to as few as 1, with honest passes unchanged. An LLM judge reading the evidence caught all 55; deterministic rules over the host record caught 27. The author's conclusion: the record is what a judge should read, not a replacement for one.

The same gap shows up in what agents declare about the outside world. YUL (listed Nov 19) found that Claude Code with Opus 5.5 declared a stale dependency version in 29% of runs, recalled from training data, and DeepSeek V4.1 Flash in 39%. A harness check against the package registry, which blocked the stale version and named the current one, got 93% and 96% of those runs onto the latest release. And Daniel Stenberg, quoted by Simon Willison on Nov 18, noted that while agents translated 185,000 lines of curl's C into 340,000 lines of Rust, the real curl merged over 200 bug fixes that none of the clones have. "Done" is a claim about a moving target.

In practice, build a ladder of evidence the agent doesn't control. CodeRabbit's CEO Harjot Gill, on The Pragmatic Engineer podcast (Nov 18), described his: formal models (TLA+, Lean) for the hardest logic, deterministic simulations that fuzz concurrent interleavings, emulated cloud APIs, real development deployments, and staged rollouts behind feature flags that an agent watches. His engineers review releases rather than individual pull requests, and anyone on the "review exempt" list loses that status after enough outage strikes. That is one CEO's account, not a measured result, but the shape matches the papers: verification lives outside the agent, and the agent's report is a pointer into the evidence, not the evidence.

Our read: ask for the report, because asking makes agents disclose. Then grade the record.

Try it this week about 2 hours
  1. Add two lines to your agent instructions: “Never special-case code to satisfy a test” and “In your final report, list every test you changed, skipped or special-cased.” Truthgate found both the warning and the request change behavior.
  2. Take your last 10 agent sessions and compare each final summary with the actual diff and CI result. Count the claims that don't hold up; that is your own unfaithful-report rate.
  3. Make CI, not the agent, the source of “tests pass”: re-run the suite on the host and keep the tool-call log somewhere the agent can't write.
  4. Add a pre-commit or PreToolUse check that compares every new dependency version against the registry (for example npm view <pkg> version) and blocks stale ones.

02 / Cost

Vendor claim

An eval measures the task; production measures how people use the model

Airbnb picked a model that won its evals at the same cost per task, then found it cost several times more per user. The lesson is to keep measuring after rollout.

Edition 1 argued for judging agents by cost per solved task. Airbnb's engineers, writing on the AWS Machine Learning Blog (Nov 18), show what happens next. Thousands of people use their internal coding-agent tool every week, through a gateway that records model, client, team and user for each request. Eight new models arrived in about five weeks, so they run two systems side by side: evals on their own tasks before rollout, scoring each model and pricing the full task at list price, and production monitoring afterwards.

The two disagreed. One model scored more than three points above the previous best on their tasks at about the same cost per task, so they rolled it out with effort capped at high. A few weeks later, average weekly spend per user on it was several times higher. Each request cost about three times as much and each user sent about three times as many. Output was only a tenth of a request's cost; most of it was cached context re-read on every turn, because the model could work on its own for a long time and people started long, self-directed sessions. In their words, the eval measured the model on a task, while production measured how people chose to work with it. When a newer model scored higher at about a sixth of the cost per task, they moved those heavy users over with a configuration change, and that group's spend fell to about a seventh with roughly the same number of requests.

The post is full of small, transferable settings. Moving one model from low to high effort raised its score by 0.8 points at 2.5 times the cost, so they set effort ceilings in the gateway. A prompt change asking for more thorough answers raised latency 40% because output grew 50%, so they treat prompt changes like deploys. And because Bedrock reserves max_tokens against your quota when a request arrives, cutting max_tokens from 4,096 to 1,024 (still above their p99 response of about 800) made each initial reservation 65% smaller and left room to admit more requests.

Two other items this week fit the same playbook. A Nov 18 paper on timeout cascades ran a small model first and escalated to a large one only when needed, cutting GPU-hours by 16 to 18% across SWE-bench tasks, and up to 33% on easy ones, with no loss in resolve rate. And prices keep moving under you: per Simon Willison, Gemini 4 Carbon's launch half-price ends Dec 1, doubling it to $4/$20 per million tokens, which makes the new Gemini 4 Neon ($3/$15) the cheaper of the two.

Our read: cost per task picks the model; cost per user per week tells you whether you picked right. Measure both.

Try it this week about 2 hours
  1. If your agents go through a gateway or proxy, add model, client, team and user to every request record, and price uncached input, cache reads, cache writes and output separately.
  2. Chart average weekly spend per user and requests per user for each model, and add a marker every time you change a default model, effort level or system prompt.
  3. Run your own eval tasks at each reasoning effort you allow, and cap effort in the gateway wherever a higher setting costs more without scoring higher.
  4. Check your max_tokens settings against your p99 response length, and lower any that are far above it if your provider reserves quota for them.

03 / Context engineering

Keep the whole log searchable, and keep the rulebook short

Three new pieces split agent memory into what to keep (everything, as plain text), what to tell the agent up front (a short, model-sized set of rules) and what the data's owner should say about it.

Edition 1 argued that an agent's memory should be a ledger, not a story. A Nov 18 paper, Forget Freely, Grep Later, tests the simplest version of that idea: an append-only plain-text log of the agent's entire history plus a regular-expression search tool, with no embeddings, no index and no extra model. Trained with reinforcement learning to use it, a Qwen3.5-9B agent scored 95 to 97% on a recall benchmark where lossy summarization and masking strategies scored at most 21%, and it stayed on the accuracy-to-cost frontier across all five tests. It is one model trained for this tool, but the lesson is cheap to apply: before building a memory system, give the agent its raw history and grep.

What the agent is told up front is a different question, and IBM's deployment report (Nov 19) gives a counterintuitive answer. Its pipeline, shipped in the open-source altk-evolve library and in IBM's CUGA and watsonx Orchestrate agents, mines short lessons from the agent's own past runs and consolidates them into guidelines. A strong model kept improving as guidelines were added: DeepSeek-V3.2 gained 9.5 points of task completion with its full set of 191. A weaker one did better with less. gpt-oss-120b went from 39.9% to 51.2% with all 199 of its guidelines, but to 55.4% with a selected subset of about 29. The authors' summary: the right amount of memory is a property of the model, not the memory. They also list what went wrong in production: a heavily supported guideline that backfired, source links silently lost during consolidation, and a swallowed API error that failed every task while producing a plausible log.

The third layer belongs to the people who own the data. On Martin Fowler's site, Simon Harrer and Arif Wider's Data Contracts (Nov 18) explains the 2026 addition to the Open Data Contract Standard (ODCS 3.2): an AI context block in the contract itself. It holds instructions ("premiums are stored in cents; divide by 100"), constraints ("don't use this data to make decisions about individual customers") and verified statements, which pair common business questions with a query the provider has checked, so an agent can reuse a correct answer instead of guessing one. The Data Contract CLI checks it all in CI: datacontract lint, breaking for breaking changes, ci to test the data, and a nightly test --server prod.

In practice, that is three layers with three owners. The runtime keeps everything, searchable. The team curates a short rulebook, sized to the model that reads it and with a link from each rule to the incident it came from. And the owner of each dataset publishes how it may be used, next to the schema rather than in a wiki.

Our read: more memory is not more context. Store everything, inject little, and let the agent search for the rest.

Try it this week about 2 hours
  1. Write each agent session's tool calls and outputs to an append-only text file, and give the agent a search tool (grep or ripgrep) over past sessions.
  2. Count the rules in your CLAUDE.md or AGENTS.md. If you run a cheaper model, try it on 10 tasks with only your top 20–30 rules and compare against the full file.
  3. Next to each rule, add a one-line note of where it came from (an incident, a review comment). Delete rules nobody can explain.
  4. Pick one table your agents query often and write an ODCS AI context for it: two instructions, one constraint and two verified queries. Run datacontract lint.

04 / Operations

A retry is not a recovery: give agent actions a ledger before they touch the world

A fault-injection study shows what it takes for an agent's side effects to survive a crash, and this week's tooling changes show where agents wait, hold resources and fail open.

When an agent's tool call is interrupted, the action may already have happened. Retry and you might send the email twice; assume it worked and you might hide an action that never occurred. Idempotency Is Not Recovery (Nov 17), a single-author study, injected ten kinds of host faults into a controlled agent runtime across 7,513 trials each on Windows and Linux. In 200 crash-and-replay pairs, the full design recorded no repeated effects, against 117 of 200 for each simpler setup. It had three parts: an action ledger that records intent before acting and the result after, an idempotency key the target system checks, and reconciliation that asks the target what actually happened on restart. Without the ledger, all 170 effects in one test were orphaned. Without reconciliation, every one of 100 crashes after the effect left the outcome unknown, even though nothing was duplicated. The price was about one-seventh the throughput of a fail-open runtime.

Waiting is the other half of agent operations. Held While Waiting (Nov 19) measured agents on Amazon Bedrock AgentCore: a median 2.7 seconds waiting for each model reply, then an estimated 5 to 40 milliseconds of compute. CPU isn't billed during the wait, but each conversation reserves its own virtual machine until it is closed, so 1,000 conversations hold 1,000 environments to do the work of 2 to 15 cores. GitHub's new gh event listen (gh v2.105.0, in preview) targets the same waste on the client side: an agent can block on a pull request event, such as a submitted review or a finished check suite, instead of polling, and gh now suggests it to agents that start polling.

And check what your safety hooks do when they break. Claude Code 2.1.329 (Nov 19) changed Code Mode so that a PreToolUse hook that errors no longer refuses the script's tool call, matching behavior outside Code Mode. A hook that must refuse on failure now needs "onFailure": "block". If a hook guards something you can't undo, decide explicitly whether it fails open or closed.

In practice, treat every agent tool that changes the outside world like a payment API. Write the intent to a ledger before the call, pass an idempotency key the target can check, and on restart reconcile by asking the target rather than replaying the call. Close agent sessions explicitly rather than letting them time out, and replace polling loops with event waits where your platform has them.

Our read: the hard part of agent reliability is not the model's judgment; it is the same distributed-systems plumbing every payment system already needs.

Try it this week about 2 hours
  1. List the tools your agents call that change something outside the session (send, pay, deploy, delete, write to a database). For each, check whether the target supports an idempotency key, and pass one.
  2. Before each of those calls, write a ledger entry (action, key, time); after it, record the result. On restart, query the target for any entry without a result instead of retrying it.
  3. If you use Claude Code hooks as safety checks, update to 2.1.329 and add "onFailure": "block" to any hook that must refuse when it errors; then break the hook on purpose and confirm the call is refused.
  4. Find one agent loop that polls for CI or review status and replace it with an event wait (for example gh event listen, if you have Event Streams access).

05 / Security

The plumbing around your models is now the attack surface

An exploited flaw in a popular AI gateway, two attacks on how agents are served and run, and a measurement of agents editing CI pipelines all point at the same unglamorous layer.

On Nov 18, CISA added a LiteLLM vulnerability (CVE-2026-40217, listed as an unprotected alternate channel flaw) to its Known Exploited Vulnerabilities catalog, which means it has evidence of active exploitation. LiteLLM is a widely used open-source gateway that sits between applications and model providers, which also makes it a natural place to hold every provider key a company has. We could not reach the vendor advisory or the CVE record to confirm the technical details, so check LiteLLM's own advisory for affected versions before acting.

Two papers this week target the serving and execution layers. BlockJack (Nov 19) attacks the block tables that vLLM uses to map each request's key-value cache onto GPU memory, much as an operating system maps pages; with Rowhammer-style faults it can redirect one tenant's request onto another's cached data. The authors report that vLLM and Sonar confirmed the vulnerability and proposed patches, which the authors validated. ToolPulse (Nov 19) needs no access to the model at all: tools run on the user's machine and share system libraries, so a cache side channel there reconstructed agents' tool workflows with F1 above 93% across 11 models in Codex and Claude Code, and still inferred the kind of task on a server shared by about 20 users.

The pipeline itself is the third layer. A study of all 932,791 agent-authored pull requests in the AIDev dataset, Who Changed the AI Agent's Rules?, separated changes to ordinary code from changes to the CI/CD control plane: workflow files and permission settings, which can widen what every later run is allowed to do. Under the author's own scoring model, control-plane pull requests carried 3.9 times the mean governance risk of ordinary ones.

In practice, put AI infrastructure on the same footing as the rest of your infrastructure. Inventory the gateways, serving engines and agent hosts you run, put them in your patch process, and keep provider keys behind them scoped and rotatable. If you serve models to several tenants on shared GPUs, follow the vLLM fixes and consider separating tenants. Run sensitive agent work on machines no one else shares. And require a human review for any agent change to workflows or permissions, however small it looks.

Our read: the model is the part everyone watches; the gateway, the cache and the pipeline are the parts attackers will.

Try it this week about 90 minutes
  1. Search your services and containers for LiteLLM, note the versions, and follow the vendor's advisory for CVE-2026-40217. Rotate any provider keys it held if you were exposed.
  2. Add a CODEOWNERS entry for .github/workflows/ and any permission files, and turn on branch protection so agent pull requests that touch them need a human approval.
  3. List every place you run vLLM or SGLang for more than one team or customer, and note whether tenants share GPUs and caches.
  4. Move agent sessions that handle secrets or customer data off shared multi-user machines.
