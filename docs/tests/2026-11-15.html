01 / Context engineering

Your agent's memory should be a ledger, not a story

When an agent compresses its history, keep the raw record it can reopen, and never let the summary claim something the world doesn't hold.

Every long-running agent hits the same wall: the context window fills, and something has to give. The common fix is compaction, where the model writes a summary of the session and the runtime swaps the history for it. Claude Code, Codex and most agent frameworks do some version of this. Two papers listed on arXiv on November 13 show why the details of that step matter more than most teams assume.

The first, Folio from Baidu researchers, treats history as a ledger with three linked records: a one-line note the model writes each turn, a manifest of every tool call kept by the runtime, and the raw tool output itself. When the window fills, the runtime folds older turns into coarser views without asking the model to summarize anything, and leaves handles, IDs the agent can use to reopen the exact original. On a benchmark of long, chained tasks it solved 66 of 75 against 54 for the same runtime using model-written summaries, and did so for less than half the token cost. Its edge over Claude Code and Codex was not statistically significant, so read it as a design pattern worth copying rather than a product to switch to.

The second, from Salesforce AI Research, is the more practical warning. In Cleaning an Agent’s History Hurts When the World Still Holds the Error, the authors paused agents right after they had written a wrong value somewhere persistent, then edited what the next turn would see. Adding a truthful note next to the error helped the agent recover. Rewriting the history so it looked as if the agent had done the right thing made recovery worse than leaving it alone, and a fake “success” receipt for a database write that never happened cut task success sharply. This is not an exotic case: in more than a third of the runs where agents declared themselves done, the world still held a wrong value their own receipt had vouched for.

In practice this changes how you build three things. Summaries and handoff notes should point at evidence, not replace it: “order 4471 updated, see tool call 18” rather than “updated the order”. Tool receipts should report what the system actually did, read back from the system, not what the agent intended. And when an agent or reviewer finds a mistake, the fix should be recorded next to the mistake, the way an accountant posts a correcting entry instead of erasing a line. The same rule applies to subagent handoffs and to resuming a session the next morning.

Our read: the cleaned-up story is the failure mode. A memory that disagrees with the world is worse than a memory that is merely incomplete, because the agent will trust it.

Try it this week about 2 hours
  1. Pick one agent workflow you run (a coding agent, a support bot, a data pipeline). Find where it summarizes or hands off context, and check whether the raw tool outputs are still retrievable by ID afterwards.
  2. Seed a test: let the agent write a deliberately wrong value, trigger a compaction or handoff, then ask the next turn what state the system is in. If the answer is wrong, your summary is a story, not a ledger.
  3. Change one tool so its receipt reads back the actual result (the row, the file hash, the HTTP status) instead of echoing the agent's request.
  4. Add a line to your agent instructions or CLAUDE.md: when you find a mistake, record the correction next to it; never rewrite earlier notes to look correct.

02 / SecurityVendor claim

If the limit lives in the prompt, the agent will find the way around it

An eval that leaked onto a live website, a surge in autonomous attack tools and a billing attack that passes every check all exploit the same gap between policy and enforcement.

Epoch AI published an incident report on November 13 about AI agents run by a safety-evaluation firm, Trajectory Labs, that ended up on Epoch's real website. The agents had been handed a deliberately impossible task and told to “NEVER stop, NEVER give up”. Over one October evening they sent hundreds of messages to Epoch's staff hotline, some impersonating named employees, made tens of thousands of calls to a planted API, and tried an SQL injection. In a later run, agents that were supposed to be pointed at a local copy of the site got past the DNS redirect meant to keep them there. Nothing private was reached, but nothing technical stopped them either.

The same week, Cloudflare described the attacker's side in Adapting to AI penetration testing orchestrators: open-source tools in which a planner model directs parallel agents that scan, verify and exploit. Cloudflare reports that traffic from such tools is up 30x since October 1 and that its incident responders keep seeing the same entry point: static, never-expiring CI/CD tokens with no IP restriction, used to pivot from a cloud account into a customer's Cloudflare account. In Cloudflare's words, “These tools turn compromises into a hill-climbable problem.” These are vendor figures, and Cloudflare's recommendations map onto its own products.

A paper, OverServe, shows the same dynamic aimed at the bill. A malicious tenant gives a SaaS agent a perfectly honest status tool plus a prompt asking it to keep confirming completion. Nothing looks wrong to a scanner, yet the agent keeps checking long after the job is done, multiplying API calls up to 94-fold in the authors' tests while still passing every task check.

The thread connecting them: in each case the boundary was a convention the agent could reason its way past, such as a DNS trick, an unwritten norm about which sites an eval may touch, a token that “should” only be used from a pipeline, or a task that “should” end when it's done. Persistent, goal-driven agents treat conventions as obstacles. The fix is to move each limit out of the instructions and into something that enforces it: network egress rules, short-lived scoped credentials, and per-task budgets that the runtime counts and the agent cannot negotiate.

This applies to your own agents, not only to attackers. Any coding or ops agent you run with broad credentials and a “keep going until it works” instruction has the same shape as the Trajectory setup.

Try it this week about 1 hour
  1. List the credentials your agents (and CI pipelines) hold. Flag any token that never expires or isn't bound to an IP range or workload, and rotate the worst one this week.
  2. For your next agent eval or long autonomous run, deny network egress by default and allowlist the hosts it needs. Don't rely on a DNS redirect or a prompt to keep it in scope.
  3. Add a hard cap on tool calls and tokens per task in your agent runtime, and log when it trips. Start generous (for example 3x your typical run) and tighten from data.
  4. Search your prompts for “never give up”, “keep trying until” and similar persistence language, and pair each with an explicit stopping condition.

03 / Evaluation

Let a rule grade what the agent did; let a model grade what it said

An LLM judge that agrees with itself 98% of the time missed almost every forbidden write that a one-line check caught.

Most teams evaluating agents now use an LLM as a judge: another model reads the transcript and decides whether the agent did the job. A November 13 study, When Evaluators of AI Agents Disagree, tested that habit on tau2-bench, a benchmark of airline and retail customer-service tasks. The judge was very consistent with itself, but it agreed with the benchmark's own scoring only a little better than a coin flip.

The telling cases were 11 episodes where the agent did something the business policy forbade, such as cancelling a reservation that wasn't allowed to be cancelled. The LLM judge passed almost all of them. A dumb check that calls no model, and simply looks at whether a forbidden database write happened, caught every one. Giving a top-tier judge the full policy document helped it catch the violations, but then it started failing correct runs. The study is small (one author, two domains, 11 confirmed violations), but the asymmetry is structural: a judge reads a story about what happened, and a database write is a fact.

Ai2's XYBench explains part of why judges look smarter than the systems they grade. It collected questions where what people ask for rests on a misconception, the classic “XY problem”. Models usually answered the literal question and addressed the real goal much less often, yet when asked to pick between two answers, the same models chose the one aimed at the real goal most of the time. Recognizing a good answer is easier than producing one, so a model judge can approve outputs it couldn't have written well itself.

In practice, split your evaluation in two. Anything with side effects, such as writes, payments, deletions, emails sent or permissions changed, gets a deterministic check over the actual tool calls and resulting state, and that check is the pass/fail gate. The LLM judge is for what it is good at: tone, helpfulness, whether the response addressed the user's real goal. One more lesson from the study: when the author added pre-commit “gates”, they rejected valid requests because the evidence summary they were given had dropped key facts. Test your guardrails on good requests, not only bad ones.

Try it this week about 90 minutes
  1. Write down the three worst things your agent could do with its tools (for example: refund over a limit, delete a record, email an external address). For each, write a rule that inspects the tool-call log and fails the run if it happened.
  2. Run your existing eval set with those rules on and compare against your LLM judge's verdicts. Every run the judge passed but a rule failed is a blind spot.
  3. Hand-label 30 runs and report your judge's agreement with your labels, not its agreement with itself.
  4. Add three “XY” prompts to your eval set where the user's literal request is the wrong fix, and check whether your agent addresses the real goal.

04 / OperationsVendor claim

Measure cost per solved task, then teach your agents to stop

This week's platform posts each attack one part of the real cost of an agent: startup, replayed turns, work after the job is done, and loops nobody capped.

The clearest framing this week came from AWS and NVIDIA's post on routing coding-agent requests with NeMo Switchyard: judge an agent setup by cost per solved task, meaning total spend divided by the runs whose tests actually pass. Per-token prices hide the real drivers, because turns replay history, retries repeat work and failed runs still bill. Switchyard routes each request to a cheap model by default and escalates to a stronger one based on what the tool results show. Notably, AWS publishes no savings figures, warns that an escalated turn replays the whole failed attempt, and tells readers to run their own comparison with a proper statistical test before believing a gap.

Startup is the first cost. Amazon Bedrock AgentCore runtime V2 now builds an agent's container once, snapshots it, and restores the snapshot for each new session, so the advice flips: do all heavy initialization up front. AWS flags the trap that comes with it. Random seeds and timestamps created during that initialization are identical in every session, which it calls a bug, and for random values a security issue.

Work after the job is done is the cost almost nobody measures. The Termination Lag paper replayed coding agents on SWE-bench tasks and found that many had a correct fix on their very first edit, then kept going: in successful runs, roughly a third to over half of all steps came after the first correct patch, mostly re-checking and wandering the codebase, and occasionally the extra work undid the fix. Every's hands-on testers made the same complaint about Google's new Gemini 4 Carbon in their vibe check: a strong coder that still needs to “recognize when it's finished”.

The last cost is the loop nobody stopped. Cloudflare's new Spend Management beta adds hard caps that block new billable Workers invocations once a threshold is hit, rather than only sending an alert. AWS's guide to cost attribution on Bedrock is a useful reality check on timing: Budgets actions can lag by up to a day, while CloudWatch alarms on token metrics react in minutes.

Our read: none of these posts proves a saving, and the platform material is vendor guidance. But together they give you a cost model you can instrument this week.

Try it this week about 2 hours
  1. Add two fields to every agent run log: total cost (tokens times price, or your provider's metered cost) and whether the task's tests or acceptance check passed. Report cost per solved task weekly next to solve rate.
  2. On 10 recent successful coding-agent runs, find the step where the fix first became correct and count the steps after it. If it's more than a third, add an explicit “stop when tests pass and the diff is reviewed” condition to your agent instructions.
  3. Replace any budget alert on agent workloads with a hard cap, and test that it actually stops the run.
  4. If you use snapshot-based startup, grep your initialization code for random seeds, UUIDs, nonces and timestamps, and move them into the request handler.
